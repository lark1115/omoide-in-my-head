# 要求の記録 — omoide-in-my-head

状態: 要求定義。ここに無い開発はしない。足りない時は、この記録を先に直す。
実行ファイルの名前は `omoide`。

## 1. 何を作るか

LLM のエージェントのための、長期記憶の装置。

エージェントは、決まりも、決めたことも、前に調べたことも、記録としては持っている。それでも、要る場面でその記録が出てこない。この装置は、**記録を、要る場面に届ける**ために作る。

## 2. 業務の要求

出どころが「利用者」の要求は、この装置を頼んだ利用者の発言による（原文は非公開の記録にある）。「調査」は文献と実測、「聞き取り」は 8 章の聞き取りによる。「案」の印が付いた要求は、利用者がまだ確かめていない。

### 2.1 装置の形

| 番号 | 要求 | 出どころ |
|---|---|---|
| BR-1 | 長期記憶の装置である。保存の層と判定の層を、差し替えられる形にする | 利用者 |
| BR-2 | 強くない Linux のワークステーションや VM で、高いスペックを求めず、負荷を小さく動く。Muse の VM を主な使い先とし、Muse でない Linux のエージェントでも動く | 利用者 |
| BR-3 | LLM が、公開の README と AGENTS.md を読んで、自分で組み込める。空の保存先から、決まりを登録し、別のプロセスと新しい会話から、その決まり（動作、またはスキルの参照先）と元の言葉を取り出す所まで、一巡できる | 利用者。一巡の形は案 |
| BR-8 | 速い判定の層（型つきの問いに確率で答えるモデルなど）を組み込める。判定の層は、ほかの物に置き換えられ、密に結びつけない。置き換えても、保存した記録は残る。外の判定の層を使うかどうかは、その鍵を渡す利用者が決める | 利用者 |
| BR-9 | 保存の既定は SQLite。Turso にも対応する。Cloudflare D1 へ寄せる時に妨げになる機能に頼らない | 利用者 |
| BR-14 | 外の鍵が無くても、SQLite に記録し、記録を引ける。判定の層について、「設定が無い」「判定して、当てはまる物が無かった」「判定に失敗した」の 3 つを、区別して返す | 案（BR-8 から） |

BR-9 の読み方: 対応を掲げる保存は、同じ試験（登録、検索、訂正、重なる書き込み）に、その実物で通す。Turso は、通った時に対応を掲げる。D1 は、対応を掲げる時に、D1 の実物で通す。

### 2.2 記憶の流れ

| 番号 | 要求 | 出どころ |
|---|---|---|
| BR-4 | 記憶が元になる。記憶の中の経験から、スキル（すぐ出せる動作、概念、物事）が生まれる | 利用者 |
| BR-5 | 明示された決まり（こうしてね、覚えておいてね）は、経験の積み重ねを待たない。登録が成功したあとの、最初の問い合わせから返る | 利用者 |
| BR-5b | 新しい決まりが入る時は、既にある決まりと照らし合わせる。同じ決まりの送り直しは、二重に持たない。当てはまる範囲が重なって食い違う時は、両方の元の言葉を示して、利用者に確かめる。確かめが済むまで、新しい方は候補のままで、今の決まりを上書きしない | 利用者。確かめが済むまでの扱いは案 |
| BR-6 | よく使う物ほど、引き出すのが速くなる。返っただけの物は「使った」に数えない | 利用者。数え方は案 |
| BR-7 | 反射的に出せる動作は、すぐ返る。遠い過去や膨大な記憶は、思い出すのに時間がかかってよい | 利用者 |
| BR-10 | 利用者の言葉は、原文のまま持つ。要約、決まり、決めたことから、元の発言（いつ、何について）へたどれる | 利用者 |
| BR-11 | 装置は、記録を自分からは消さない。置き換えられた記録には、置き換え済みの印を付ける。ふだんの問い合わせには今の版が返り、履歴を指定すれば前の版が返る。保存できなかった時は、成功として返さない | 案（BR-10 の前提。調査） |
| BR-12 | 経験からスキルへ上げる所に、関門を置く。経験は候補になり、確かめてからスキルになる。確かめるのは、ふだんは LLM 自身。既にある決まりと食い違う時だけ、利用者に聞く | 調査。確かめる者は利用者が決めた |
| BR-13 | 事実（決めたこと、知っていること、済んだこと）は、決まりやスキルとは別の種類の結果として引ける | 案（調査、聞き取り） |

BR-5 と BR-12 の関係: 利用者が明示した決まりは、関門を通らない（BR-5）。関門を通るのは、経験から作った候補だけである（BR-12）。

### 2.3 場面に届ける（聞き取りから）

| 番号 | 要求 | 出どころ |
|---|---|---|
| BR-16 | 決まりは、使う場面と動作に結びつけて持つ。場面と、しようとしている動作で問い合わせると、有効な決まりと、その条件、参照先が返る。当てはまらない場面では返らない | 案（聞き取り） |
| REQ-RULE-1 (b)、REQ-RECALL-1 (b) | 決まりに、守る目的と、当てはめない範囲が記録されていれば、決まりと一緒に返る。記録に無い目的や例外は「不明」と返し、装置も LLM も作らない | 案（聞き取り） |
| BR-18 | 決めたことは、発言の種類（指示／提案）と、今の状態（判断待ち／決定済み／改められた）を、別々に持つ。対象と時点と元の言葉と一緒に返る。判断待ちを、了承として返さない | 案（聞き取り） |
| REQ-DEC-1 (d)(e) | 記録は、人から聞いた物か、自分で確かめた物かを区別して持つ。確かめた物には、どこで、いつ、何で確かめたかを持たせる。「頼んだ」と「相手に届いたと確かめた」、「入力した」と「使えると確かめた」を、別の記録として持てる | 案（聞き取り） |

BR-16 が約束する範囲: 装置が約束するのは、**問い合わせられた時に返すこと**までである。LLM が動作の前に問い合わせるかどうかは、装置を組み込む側（ホスト）の仕事で、装置だけでは保証できない。そこで、試験を 2 つに分ける。

| 試験 | 何を見るか |
|---|---|
| 装置の試験 | 問い合わせた時の戻り値。当てはまる場面と、当てはまらない場面の両方 |
| 組み込みの試験 | 同じ依頼で、動作の前に結果が LLM に届いたか。届いた結果を LLM が使ったか。この 2 つを別々に記録する。呼ばれなかった回も分母に残す |

### 2.4 測り方

| 番号 | 要求 | 出どころ |
|---|---|---|
| BR-15 | 効果は、装置がある時と無い時を、同じ場面の集まりで比べて測る。見る物は、動作の前に使われた割合、要る物が全部返った割合、関係ない物や前の版を返した割合、LLM の入力に足した量。場面と正解は、測る前に決めておく | 案（調査） |
| BR-20 | 決まりができたあとに、同じ種類の指摘が何回起きたかを、同じ種類の機会の数と一緒に、記録から数えられる。機会が 0 回の時は、成功に数えない | 案（聞き取り） |

「速い」「遅い」の定義: 保存の速さの差ではない（1 万行では、どの保存も 1 ミリ秒未満）。**最初の 1 回の問い合わせで返るか、2 回目の、時間のかかる探し方が要るか**で分ける。よく使う物は、最初の 1 回で返る側に入る。測る時は、最初の 1 回で当たった割合、問い合わせの回数、プロセスの起動を含む時間を、別々に測る。

## 3. 対象外

利用者が外した物:

- 感情や気分の仕組みとのつなぎ。
- 外の判定の層へ何を送るかの決まり（鍵を渡す利用者の選択）。

最初の版に入れない物（案）:

- 特定の利用者の環境に特有の物（設定、フック、指示ファイルの中身）。例と試験のデータは、作り物の場面で書く。
- 意味の近さの検索（埋め込み）。ただし、「違う言い方でも、関係する決まりを引ける」という試験は残す（8 章の S1）。どの方式で通すかは、測って決める。
- 外との同期、画面。

## 4. 装置では解けないこと

- 確かめずに言う、指示を提案と読み替える、仕事の質、文体。これらは記憶の問題ではない。
- 決まりができる前の、初めての失敗。防ぐのは 2 回目である（BR-20）。
- LLM が装置を呼ばなかった回。実際に送信を止めたり、権限を与えたりするのは、ホストの仕事である。

## 5. 設計の前提

### 5.1 使う場の縛り

- 想定する場の 1 つ（Meta の Muse の VM）には、依頼が届いたターンに、道具を自動で走らせて結果を入力へ差し込む仕組みが無い。装置を呼ぶかどうかは、LLM が決める。**LLM が装置を呼ぶ割合が、効果を決める**（BR-15）。
- 同じ実行ファイルが、複数のプロセスから同時に呼ばれることは、日常的に起こる。
- 道具から起動したプロセスは、長くは生きられない場がある。常駐するプロセスを前提にしない。途中で止まっても、次の呼び出しで続けられる形にする。
- 常に読み込まれるファイルに決まりが書いてあっても、その場面で思い出されるとは限らない（聞き取り）。読み込まれることと、場面で思い出すことは別である（BR-16）。

### 5.2 三つの段（案）

| 段 | 何をするか | 呼び出し |
|---|---|---|
| 段 0 | 一番よく使う物を、常に読み込まれるファイルの 1 節として `omoide` が書き出す。大きさに上限を置く。場面と動作の言葉で書く | 0 回 |
| 段 1 | LLM が `omoide` を 1 回呼ぶ。判定の層があれば使う | 1 回 |
| 段 2 | 時間のかかる探し方（古い記憶、広い範囲） | 2 回目 |

BR-6（よく使う物ほど速い）は、物が段 2 → 段 1 → 段 0 へ上がることで形にする。

### 5.3 保存

- 既定は SQLite。対応先は Turso。D1 は、寄せられる書き方を保つ（BR-9）。日本語を区切る処理、順位付け、結果の合成は、保存の外（核）が持つ。対応を掲げる保存は、同じ試験に通す。
- 日本語の全文検索は、区切った文を別の列に持ち、空白で索引する。保存の側に、自前の区切り方を登録しない（D1 と Turso では登録できない）。
- 保存の口は 2 つ: 「文の束を、まとめて成功か失敗かで実行する」と「問い合わせる」。途中で読んでから書く形のトランザクションは使わない（D1 に無い）。
- D1 の縛り（公式の文書、2026-11）: 1 つの問い合わせの変数は 100 個まで、1 行は 2 MB まで、文は 100 KB まで。
- BR-6 を守ると、「使った」と知らされるたびに書き込みが起きる。既定の SQLite は、WAL と待ち時間の設定で、複数のプロセスからの書き込みを順に通す。

### 5.4 実測（2026-11、macOS のワークステーション。強くない Linux での実測は、まだ無い）

- Turso 0.8.3 は、区切った文を別の列に持つ形で、日本語の検索 9 問すべてに通った。用意された 2 文字区切りだけでは通らなかった。全文検索と複数プロセスは実験的な設定。Rust 1.90 以上が要る。重なる書き込みは試していない。
- 1 万行での検索は、Turso も SQLite も 1 ミリ秒未満。
- 判定の層の例（Jev 1.14.0）: 言い換えた依頼から当てはまる決まりを選ぶ試しで、言葉の一致だけの探し方を大きく上回った。試しの問題は非公開なので、数字は載せない。公開できる作り物の問題で測り直す。

### 5.5 調査から取った考え

- 全部の経験を手続きに足すと悪くなり、選んで足すと良くなる（arXiv:2505.16067）。手続きへの書き込みは、ほかの記憶への書き込みより危ない（CoALA）。→ BR-12
- 起きたことと、今の事実を分ける。古い事実は消さずに、無効の印を付ける（Zep / Graphiti、gbrain）。→ BR-11、BR-13
- 置いただけの道具は呼ばれない。常に読み込まれる索引は呼ばれやすい（Vercel の測定、Agent Workflow Memory）。→ BR-15、段 0
- 検索が全体の時間に占める割合は小さい。保存を小さくして、探す時に計算する手がある（LEANN）。→ 最初の版では埋め込みを持たない

## 6. 仮の物差し（基準にする機械と線を決めるまで、仮の物）

| 物 | 仮の線 |
|---|---|
| 1 回の呼び出し（判定の API の時間を除く） | 0.1 秒以内 |
| メモリ（最大） | 50 MB 以内 |
| 待っている時の omoide のプロセス | 0 |
| 実行ファイル | 20 MB 以内 |
| LLM に返す量 | 4,000 バイト以内 |
| GPU、ネットワーク | 基本の経路では前提にしない |

測る時は、機械の CPU とメモリ、記録の数と言語と長さ、同時に動かす数、初回か 2 回目以降かを、一緒に記録する。判定の層を含む時間と含まない時間を、両方出す。macOS での結果を、Linux の合格に使わない。

## 7. 決まっていないこと

- 何回くり返したら、経験を候補にするか（測った研究が見つかっていない）。
- 何を「使った」と数えるか（LLM が採用したと知らせた時か、動作が成功した時か）。
- 「すぐ」「時間がかかってよい」の秒数。基準にする機械。
- 記録を持つ期間と、利用者による削除。
- 最初の版で Turso と D1 の対応を掲げるか。
- 意味の近さの検索を足す条件。

## 8. 合格の条件の種（聞き取りから）

エージェントが利用者から強く指摘された場面を、エージェント自身に振り返らせた（中身は非公開）。場面は、次の型に分かれた。

- 決まりは書いてあったが、その場面で出てこなかった。
- 決めたこと・調べたことは記録にあったが、その場面で出てこなかった。
- 記録が、置き場の仕組みで読み込まれていなかった。
- その時点では、決まりが無かった。
- 記憶の問題ではない。

この振り返りは、選ばれた失敗の集まりである。試験の場面を選ぶ材料として使い、頻度や改善の割合の根拠には使わない。「記録はあった」型の場面が、検索が当たるだけで全部解けるとも言わない。

そこから、一般の形に直した場面（試験では、元の場面とは別の言い換えと、当てはまらない場面も作る）:

| 番号 | 場面 | 合格 | 要件 |
|---|---|---|---|
| S1 | 利用者が、ある失敗に決まりを言った。後日、言い方の違う同じ場面で問い合わせた | その決まりが、最初の問い合わせで返る | REQ-RULE-1 (d)、REQ-RECALL-1 (e)(i) |
| S2 | 決まりがある動作（画面を読む、送る、消す）の名前で問い合わせた | 結びついた決まりが返る。関係ない動作では返らない | REQ-RULE-1 (a)、REQ-RECALL-1 (c)(d) |
| S3 | 利用者が前に決めたことについて問い合わせた | 「決定済み。いつ、どう決めたか」と元の言葉が返る | REQ-DEC-1 (a)(b)(c) |
| S4 | 「できない」「持っていない」と言う前に問い合わせた | 前に渡された物の在りか、前に確かめた事実が返る。秘密の値そのものは持たない | REQ-REC-1 (g)、REQ-DEC-1 (d)(h) |
| S5 | 済んだ作業と同じ対象と範囲の作業を、違う言い方で問い合わせた | 済んだ範囲と証拠が返る。対象や期間が違う作業では、「済んでいる」と返らない | REQ-DEC-1 (g)(h) |
| S6 | 決まりを当てはめるか迷う場面で問い合わせた | 決まりと一緒に、記録された目的と、当てはめない範囲が返る。記録が無ければ「不明」 | BR-17 |
| S7 | 条件つきの許可を要約した記録を読んだ | 元の言葉へたどれ、条件が落ちていないかを確かめられる | REQ-REC-1 (b)(c) |
| S8 | 聞いただけの話と、「頼んだ」だけの作業を記録した | 「確かめていない」として返る。済んだ事実として返らない | BR-19 |
| S9 | 記憶が何万字に増えた | 常に読み込む量は上限を超えない。古い記録も、探せば出る | REQ-HOT-1 (b)、REQ-REC-1 (e)、REQ-RECALL-1 (g)(i) |
| S10 | 同じ動詞で、対象や案件が違う 2 つの依頼 | 片方には有効な指示と元の言葉、もう片方には「当てはまらない」か「判断待ち」が返る | REQ-RULE-1 (a)(e)、REQ-RECALL-1 (c)(d)(h)、REQ-DEC-1 (c) |
| S11 | 同じ決まりを 2 つの会話から直している途中で、片方が途中で止まった | 起動し直したあと、今の版、候補、出どころが食い違っていない。使った回数の書き込みに失敗しても、決まりは失われない | REQ-STORE-1 (b)(e)(f)、REQ-PROMO-1 (i) |
| S12 | 判定の層の鍵が無い／判定が時間切れになった | 記録は引ける。「設定が無い」「失敗した」が、「当てはまる物が無い」と区別して返る | REQ-JUDGE-1 (b)(c)(d) |

## 10. 検証の進め方

- 要件ごとに、試験を先に書く。試験の強さは、わざと壊した実装を検出できることで確かめる。
- 純粋な判断（照らし合わせの結果、関門、順位、量の上限）は、性質の試験と全数の列挙で確かめる。重なる書き込みと、途中で止まった時の状態は、状態の遷移の検査で確かめる。
- 見つかった誤りは、直す前に、試験に足す。
