# ADR-0001: 部品の分け方、保存の口、表、順位付け、命令

- 状態: 確定（最初の実装の入力）
- 関係する要件: DOC-OMOIDE、REQ-STORE-1、REQ-REC-1、REQ-RULE-1、REQ-DEC-1、REQ-PROMO-1、REQ-RECALL-1、REQ-JUDGE-1、REQ-HOT-1、REQ-MEASURE-1、REQ-INTEG-1、REQ-RES-1

## 決定 1: 部品は 3 つ。核は入出力を持たない

| 部品 | 役目 | 持たない物 |
|---|---|---|
| `omoide-core` | 文の区切り、当たりの点、順位付け、近い決まりの判定、登録の結果の決定、関門、量の上限に収める整形。全部、純粋な関数 | ファイル、時計、乱数、通信 |
| `omoide-store` | 保存の口（決定 2）と、SQLite の実装。表の定義と移行 | 判断 |
| `omoide`（実行ファイル） | 命令（決定 6）。時計、識別子、設定、判定の層の起動、ファイルへの書き出し | — |

時刻と識別子は、実行ファイルが作って核へ渡す。核の関数は、同じ入力に同じ出力を返す。性質の試験と全数の列挙を、核に当てる。

## 決定 2: 保存の口は 2 つ。読んでから書く時は、束に「前提の検査」を入れる

```
exec_batch(文の束) -> 成功 | 失敗（全部か、無か）
query(文)          -> 行の集まり
```

D1 には、読んだ結果を使って続きを書くトランザクションが無い。そこで、読んでから書く操作は、次の形にする（REQ-STORE-1 (e)）。

1. `query` で、今の状態と、保存の版の番号を読む。
2. 核が、書く文の束を決める。
3. 束の先頭に、「版の番号が、読んだ時と同じである」ことを検査する文を入れる。同じでなければ、この文が制約の違反で失敗し、束の全体が取り消される。束は、版の番号を 1 つ上げる。
4. 失敗したら、1 からやり直す。回数の上限を超えたら、「ほかの書き込みと重なった」と返す。

検査の文は、NOT NULL の列へ、条件が偽なら NULL を入れる形にする。自前の関数とトリガーは使わない。

読まずに足せる書き込み（呼び出しの記録、「使った」の知らせ）は、検査を入れず、版の番号も上げない。足す文だけを束にする。

送り直し（REQ-STORE-1 (f)）は、呼び出しごとの識別子に一意の制約を置いて見分ける。同じ識別子の 2 回目は、1 回目の結果を返す。

### 試したこと

SQLite 3.51（Python の sqlite3、WAL、待ち時間 5 秒）で、次を確かめた。

| 試し | 結果 |
|---|---|
| 古い版の番号で束を実行する | 束の全部が取り消された。版の番号も上がらなかった |
| 9 個の別プロセスが、読んでから書く束を、各 100 回くり返す。1 個は、38 回目の束の途中で強制終了する | 書けた束は 837 個（800 + 37）。行は 837、版の番号は 837、重複は 0。途中で止めた束の行は、残らなかった。やり直しは、プロセスごとに 64〜154 回 |

試していない物: `rusqlite` からの実行、D1 の実物、Turso の実物。実装の時に、同じ試しを契約の試験として書く。

## 決定 3: 表

| 表 | 中身 |
|---|---|
| `meta` | 表の版、保存の版の番号 |
| `utterance` | 発言。本文、時刻、話した者の種類。更新と削除をしない |
| `record` | 決まり、決めたこと、事実、経験、スキル。種類、状態（今の版／候補／判断待ち／置き換え済み／退けた）、本文、場面、対象、目的、当てはめない範囲、発言の種類、決定の状態、確かさ、確かめた根拠、範囲、期間、証拠の参照先、常に出す印、置き換えた版 |
| `binding` | 記録と、動作の名前 |
| `source` | 記録と、出どころ（発言か経験）の結びつき |
| `text_index` | 探すための列。記録の識別子、2 文字ずつ区切った文、1 文字ずつ区切った文（どちらも空白区切り） |
| `use_log` | 返した、使った、成否、指摘。記録の識別子、機会の識別子、時刻 |
| `call_log` | 呼び出しごとの識別子、時刻、種類、かかった時間、返した量 |

- 記録を改める時は、新しい行を足し、前の行の状態と「置き換えた版」だけを書き換える。本文は書き換えない。
- 全文検索の索引の作り方（SQLite と D1 の FTS5、Turso の Tantivy）は、保存の実装が持つ。核が渡すのは、区切り済みの文だけである。

## 決定 4: 文の区切りと、当たりの点は、核が持つ

- 区切り: 文字の正規化（NFKC と小文字化）のあと、日本語の文字の並びを 2 文字ずつずらして区切り、1 文字ずつの語も別の列に入れる。英数字は、そのまま 1 語にする。
- 保存の全文検索は、候補を集めることにだけ使う。保存が返す点（bm25 など）は、順位に使わない。保存の種類で点が変わり、記録の全体の統計にも依るためである。
- 当たりの点は、核が、問い合わせの語のうち、候補の文に含まれる語の割合から数える。候補が 1 件増えても、ほかの 2 件の点は変わらない。
- 言い方の違う問い合わせ（REQ-RECALL-1 (e)）を、この数え方と判定の層でどこまで通せるかは、固定した場面で測って決める。足りなければ、意味の近さの検索を、別の ADR で足す。

## 決定 5: 順位付けと、近い決まり

- 順位: 先に、当てはまるかどうかで絞る（今の版、対象、当てはめない範囲）。次に、動作の名前で結びついた決まりを先頭に置く。残りは、点 = 当たり + 使った回数（頭打ちあり）+ 新しさ（半減）の順。同点は、識別子の順。
- 判定の層がある時は、その答えを、当たりの点の代わりに使う。失敗した時は、核の当たりの点に戻る。
- 近い決まり（REQ-RULE-1 (c)）: 動作の名前が 1 つでも重なる、または、当たりの点が線以上。線は設定の値。
- 登録の結果は、近い決まりの有無と、呼び出した側が選んだ関係から、核の関数が決める。関係の選び方（5 通り）と結果（5 通り）の組は、全数を列挙して試験する。

## 決定 6: 命令

| 命令 | 役目 | 要件 |
|---|---|---|
| `omoide init` | 保存先を作る | REQ-INTEG-1 |
| `omoide say` | 発言を、原文のまま入れる | REQ-REC-1 |
| `omoide rule add` | 決まりを登録する。近い決まりがあれば、それを返して終わる。関係を添えた 2 回目の呼び出しで、登録を終える | REQ-RULE-1 |
| `omoide resolve` | 判断待ちに、利用者の判断を登録する | REQ-RULE-1 |
| `omoide decide` / `fact add` / `event add` | 決めたこと、事実、経験を入れる | REQ-DEC-1、REQ-REC-1 |
| `omoide skill propose` / `skill confirm` / `repeated` | スキルの候補、確かめ、くり返された経験の一覧 | REQ-PROMO-1 |
| `omoide recall` | 問い合わせ。`--scene`、`--action`、`--target`、`--deep` | REQ-RECALL-1 |
| `omoide used` / `outcome` / `corrected` | 使った、成否、指摘を知らせる | REQ-PROMO-1、REQ-MEASURE-1 |
| `omoide show` | 識別子で、本文の全体と履歴を引く | REQ-REC-1 |
| `omoide hot export` / `hot status` | 常に読み込まれる節を書き出す。節が古いかを答える | REQ-HOT-1 |
| `omoide stats` | 回数、指摘、検査に変える候補を出す | REQ-MEASURE-1 |
| `omoide eval run` / `eval diff` | 決めた場面を流す。2 つの版を比べる | REQ-MEASURE-1 |

どの命令も `--json` を選べる。失敗は、0 でない終了コードと、理由の文で返す。

## 決定 7: 判定の層は、別のプロセス

実行ファイルは、設定された命令を起動し、標準入力へ問い（問い合わせの文と、候補の文の並び）を JSON で渡し、標準出力から、候補ごとの答えを JSON で受け取る。時間の上限を置く。設定が無ければ、起動しない。核と保存は、通信の部品に依らない。Jev の付け方は、別の部品として、あとで足す。

## 決定 8: 作る環境と、配り方

- Rust は 1.88 以上。SQLite は `rusqlite` の同梱版（FTS5 つき）。
- Turso の実装は、別の feature にする（Rust 1.90 以上が要るため、既定のビルドに入れない）。D1 の実装は、対応を掲げる時に足す。
- Linux（x86_64、aarch64）の、1 つで動く実行ファイルを配る。
- CI は、lint、型の検査、ビルド、`miwa check`、命令が起動する最小の検査に限る。重い試験（重なる書き込み、変異の検出）は、PR の前に手元で回し、結果を PR に書く。

## 決定 9: 作る順と、役目

| 段 | 中身 | 終わりの条件 |
|---|---|---|
| 1 | 核の区切りと点、保存の口と SQLite、`init`、`say`、`rule add`、`resolve`、`recall`、`show` | 場面 S1、S2、S6、S7、S10、S11 の試験が通る。REQ-INTEG-1 (a) の一巡が、手元の Linux で通る |
| 2 | `decide`、`fact add`、`event add`、`used`、`outcome`、`corrected`、`stats` | 場面 S3、S4、S5、S8 が通る |
| 3 | `hot export`、`skill`、`repeated`、判定の層の口、`eval` | 場面 S9、S12 が通る。資源の線を Linux で測る |

- 実装は、ワーカーが、ブランチと PR で行う。設計した者は実装せず、自分で検査を回して、要件ごとに合否を出す。
- 場面 S1〜S12 の試験のデータと正解は、実装するワーカーとは別の者が作る。

## 決めないこと

- 意味の近さの検索（決定 4）。
- 回数の線（何回のくり返しで一覧に出すか）。設定の値にして、既定を仮に置く。
