# 架空のパン工房を使った受入場面

[業務要求 §8](../../docs/requirements.md) の S1〜S12 を、新しいプロセス・会話から試すための正解データ。実行順と件数は [manifest.json](manifest.json) にある。第1段階の S1、S2、S6 だけでも実行できる。すべて架空の発言・日時・物品で、オンラインサービスは使わない。

## 読み方

1. 各ケースを空の保存先から始め、場面ファイルの `records` を先頭から登録する。レコードの `id` は期待値を照合するための名前。登録で得た実際の識別子に対応づけ、検索語には混ぜない。`relation` がある登録は比較対象 `to` への `revision`（言い直し）、`uncertain`（判断待ち）、`unrelated`（別の話）を選ぶ。配列 `actions` は一つの規則が持つ複数の動作名。`target` のない規則は全対象用。日英を併記した本文も**一つの発言**として保存する。決まりや事実の生成時は `source` を引き継ぐ。
2. `before_query` があれば同名の `preparations` の手順を順に行う。次に、前の会話・期待値・理由を渡さず、`query` だけを新しい読み手に渡す。`language` は照会側の言語。`scene` が自由文、`action`、`target`、`period`、`scope` は指定されたときだけ使う条件。`question` は ID 指定・履歴・節の読み取りを依頼する自然言語で、全文検索に足さない。正解を得るための再照会や翻訳語追加はしない。
3. 返った ID を `expect.must`（全部必要）・`must_not`（一つでもあれば失敗）と照合する。順不同。他の ID はこの二集合だけでは判定しない。`fields` は指定されたレコードの項目の部分一致、`meta` は結果全体または事後条件の部分一致。文字列・数値・真偽値はその値、範囲リストは集合として比べる。`unknown` は情報不足、`pending` は判断待ち。対象が未確認であることは検索結果ゼロとは異なる。負例で関連レコードを返しても、状態を区別すべきケースがある。ケースの `reason` は採点者専用。
4. 読み取りの形は CLI の引数ではなく観測したい結果を名付けている。`recall` は通常の初回検索、`show` は ID の本文、`sources` は指定レコードが指す原発言、`history` は指定版とその改訂前の版。`decision`・`completion`・`verification` はそれぞれ決定の状態、完了した範囲、主張を確認できたかを読む。これらは実際の照会結果とその参照をアダプターで照合できる。`section` は書き出された節を直接読む。フィクスチャのフィールド名や状態名そのものを製品の出力形式として要求しない。

### 操作と判定の取り決め

- S1 の `shared` は中心となる語の反復、`partial` は手掛かりが部分的に重なる言い換え、`zero` は語彙の重なりがない照会。正解規則の本文・場面・動作名をつないで NFKC＋小文字化し、英数字の連続と日本語の各文字を比較する。日本語の単字が重ならなければ二字組も重ならない。各言語に3難度の正例と無関係な負例がある。`lookup_calls: 1` は最初の検索結果での命中。難問の未達はそのまま記録する。
- S11 の `prepare_revision` は2人が同じ `base` を見て、それぞれ `source` の本文で元規則を言い直す準備。場面・動作・対象は元規則を継ぐ。`id` は完成した場合の版に付ける試験用の名前。`start_uncommitted_write` で右の保存処理を始め、`interrupt_before_commit` で確定前に停止する。左は `commit` で確定後、`lose_reply_and_restart` で応答を失いプロセスを作り直す。`retry` では同じ入力・同じ `request` を再送する。履歴の `exact_versions` は当該規則の版数。未確定版の名前は非出現の照合にだけ使う。`fail_usage_accounting` は検索結果を組み立てる際に付随する回数記録だけを失敗させる。再起動後に同じ規則と出典を読めたことを `survives_restart` とする。故障注入や停止位置を制御できないアダプターでは「未実施」と記録し、合格にはしない。
- S9 の `seed_experiences` は0から count−1の順に、指定の架空の文と通番を本文に持つ別々の出来事を作る。識別用の名前は `id_prefix-通番`。日時は2040年4月20日00:00 UTCから通番分だけ分を足し、対象は bakehouse とする。候補化・採用通知はしない。`initialize_section` で専用の空ファイルに印を作り、`export_section` で書き出す。`max_section_bytes` は印を含むUTF-8バイト数の上限。`section` の ID は節に表現された規則の意味に照合し、ID文字列の印字を要求しない。
- S12 の判定器は決定的な試験条件。`no-key` は未設定、`timeout` は設定済みだが時間切れ、`valid-empty` は設定済みの判定器が候補を正常にすべて非該当と判定。前二者は基本検索で見つかる語、後者は候補があるが意味の違う語を使う。`judge_state` と `result_count` は独立して照合する。

## 対応表

| 段階 | 場面 | 観測すること | 主な条項 |
|---|---|---|---|
| 1 | S1 | 初回の言い換え検索 | RULE(d)、RECALL(e)(i) |
| 1 | S2 | 動作名だけの正負 | RULE(a)、RECALL(a)(c)(d) |
| 1 | S6 | 目的・適用除外の記録と不明 | RULE(b)、RECALL(b) |
| 2 | S7 | 異なる要約から個別の原文へ | REC(b)(c) |
| 2 | S10 | 同じ動詞、異なる籠、未解決の関係 | RULE(e)(g)、RECALL(c)(d)(h) |
| 2・3 | S11 | 中断・再送・旧版の出典／回数保存の失敗 | STORE(b)(e)(f)、REC(d)(e)、PROMO(i) |
| 3 | S3 | 発言種別、決定状態、時点と原文 | DEC(a)(b)(c) |
| 3 | S4 | 引換票の所在と観測の根拠 | REC(g)、DEC(d)(f)(h) |
| 3 | S5 | 部分完了、期間や対象の食い違い | DEC(g)(h) |
| 3 | S8 | 伝聞と完了確認の区別 | DEC(d)(e) |
| 4 | S9 | 節の上限、現行版と履歴 | HOT(b)(d)(f)(g)、REC(e) |
| 4 | S12 | 判定不能、正常0件、基本検索 | JUDGE(b)(c)(d) |

各略記は `req/REQ-略記-1.md` の条項。リポジトリのルートで次を実行すると、Python 標準ライブラリだけでデータ・件数・参照・引用・S1の語の重なりを検査できる。製品の合否は実装アダプターで各ケースを実行して判定する。

```sh
python3 tests/scenes/tools/validate.py
```
