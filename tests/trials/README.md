# 長期記憶で作業の間違いが減るか

架空のパン工房で、同じ48機会を3条件で対にして比べる。答えるのは利用者への**作業手順、判断、報告**。検索に当たったことだけで合格にはしない。各機会は独立で、他の回答・訂正は引き継がない。設計の根拠は [業務要求 §2.3・2.4・4](../../docs/requirements.md) と [計測要件 (e)〜(h)](../../req/REQ-MEASURE-1.md)。

| 機会 | 日本語 | 英語 | 主集計 |
|---|---:|---:|---|
| 既存の規則を場面で使わない／済んだ決定を聞き直す／ある物・確認済みの事実をないと扱う／完了した作業をやり直す／規則を適用外に広げる／伝聞を確認済みと扱う | 各3 | 各3 | 36件 |
| 既存記憶が該当しない対照（過剰適用を検出） | 4 | 4 | 8件 |
| 現物を見ずに現況を確定すること、文章の質や文体など、装置単独では解けない課題 | 2 | 2 | 除外4件 |

## 入力・記憶・採点表

- `opportunities.json` は、意味を符号化しない機会ID・言語・利用者の依頼だけを持つ。モデルに渡すのはその1件の `prompt` 本文だけ。
- `memory.json` は全機会が同じ時点で持つ全48記録。ケースごとの正解だけを選んでロードしない。規則は適用場面・動作・対象・例外と所有者の元発言、決定は対象・発言種別・決定状態・決定時刻と元発言。確認済みの事実は先にある経験IDを根拠に持ち、経験には観察した時点・対象・内容がある。伝聞の事実は交代担当の発言に由来する。値のない例外リストは、この発言に例外が記載されていないことを表す。論理IDを内部IDと対応付けて登録し、入力された元の文を保持する。伝聞の文を取り込む場合は「交代担当からこの文を聞いた」という経験として出典を表現してもよい。登録処理が近い規則を提示したら異なる対象・用途として元の両方を保つ。この架空時点から試行中に現況が変わったという追加情報はない。
- `hot.txt` は、全試行に使う固定の常時読込節（末尾改行を含むUTF-8）。工房の定番作業を日英各2件選んだ。各依頼に合わせて中身を変えない。これは常時注入の効果を比較する実験条件で、節を選ぶアルゴリズムの評価には使わない。
- `grading/key.json` は機会ごとの動作の境目、正しい振る舞い、既知の失敗、種類、関連要求、根拠となる記憶ID。scope_overreach の根拠IDは**適用外と判定する**ための参照。control／outside の空リストは全記憶を用意した上で該当なしを示す。`grading/examples.json` は採点者の練習用の架空発話12例。どちらもプロンプト・検索候補・ホストのファイル検索に入れない。
- `manifest.json` は言語・種類・集計対象の件数、条件、固定ファイルのSHA-256。検証はルートから `python3 tests/trials/tools/validate.py`。これはデータ検査で、モデルやサービスを呼ばない。

## 三条件の実施

1. main に凍結したコミットと manifest を先に記録する。同一機会の3試行は同じモデル・設定・ツール時間予算・ユーザー依頼・言語・共通システム指示で、新規の会話と同じ初期状態から始める。共通指示は日本語「次の工房の依頼に答えて。何をするか、そのまま担当に渡せる形で決めて。まだしていない作業を済んだとは言わないで。」、英語 “Answer the workshop request with a decision or instructions the next shift can use. Do not claim to have performed work you have not done.”。正解の行動や規則名を加えない。
2. 全条件で従来の手段として同じ工房台帳を任意に読めるようにする（memory.json の原文とメタデータ、通常の一覧・文字検索）。台帳の全件を最初の入力に貼らない。こうすると装置なしでも、エージェント自身が従来の台帳を確かめれば正答できる。利用可能な手段の説明は同機能なら同文とする。公開リポ全体へのアクセスは与えない。
3. `no_device` は共通の台帳だけ。`hot_only` は同じ台帳に hot.txt の注入を追加。`device` は同じ台帳・同じ節に、同じ記録を登録した omoide の任意照会を追加する。強制呼出しはしない。内部の正解IDで検索を代行しない。これで hot_only 対 no_device は常時注入の増分、device 対 hot_only は照会機能の増分を比べられる。モデルに条件名を伝えない。使えるツールから条件を推察できるため、盲検の対象は採点者。
4. 48件×3＝144試行を事前割当する。6通りの条件順を機会ID順に循環させて各順8件にする。乱数・モデル版を固定または記録する。失敗した試行を別の依頼に置き換えない。新規会話へ依頼の原文を渡し、最初の作業方針・指示・報告を採点点とする。外部で実際に発注や作業はしない。記録参照だけで済む問い合わせは自由。好みの条件だけに追加の助言や訂正を与えない。
5. 第三者が採点用コピーを作る。ランダムな採点票IDを振り、条件名・ツール名・ツール呼出しと戻り値・タイムスタンプ・追加コンテキスト・実行順を外す。アシスタントの最終的な作業内容・対象・確認状態、利用者依頼は残す。「検索で確認した」など経路を特定する部分だけ中立化し、物品名や判断の理由は残す。採点者はこのコピーと当該機会のキーを読み、条件や他条件の回答を見ずにラベルと根拠箇所を記入する。

## 観測の受け渡し

固定入力と実行後の観測は別ファイル。観測器は [eval run --trials の入力仕様](../../README.md) に従い、**JSON配列**の各行に次の項目を置く。モデルを動かしていない時点では観測行を生成しない。

| 項目 | 記録するもの |
|---|---|
| opportunity, variant | 機会IDと device / no_device / hot_only。対を解除する対応表は採点後にのみ結合。 |
| called | その試行での装置照会の有無。共通台帳の読み取りや節の注入を装置照会に数えない。 |
| delivered_at, acted_at | 同一時計で、関連する結果が入力に届いた時と、最初に作業判断を確定した時。節から届いた場合も記録する。該当なし・時点不明は null。遅れて届いたものを有効な事前利用にしない。 |
| used, action, corrected | 採用が観測できたか、選んだ行動、利用者による同種の指摘が実際にあったか。正しい回答だけで採用済みとは推測しない。採用不明は別の原観測に残し、集計で事前利用成功と数えない。 |
| added_input | 実際にモデルへ追加した節・装置応答を入力順に保存する。未使用条件では空文字。UTF-8バイトで集計する。共通台帳からの入力とツール説明の差は別に記録し、総入力コストも比較できるようにする。 |

一つの機会で複数照会があっても試行は一つ。元の観測に照会ごとの返却ID・順序・内容を保存し、キーを開いた後で必要記録の全件命中、無関係な記録の提示、事前到達を確認する。観察不能な順序は不明として残す。CLI の利用・到達集計とは別に、次の採点結果を機会IDで結合する。

## 盲検採点

対象は**最終的に選んだ行動**。言葉の一致、検索したという宣言、正解らしい記録の単なる列挙には点を付けない。実行指示でも実行したという証明は不要。ケースの pass / known_mistake の同義表現を認める。条件付きの一案を最終決定と読み替えない。

| ラベル | 判定 |
|---|---|
| pass | 必須の判断を具体的に示し、既知の失敗を採用していない。偶然当たっていても行動得点は同じ。 |
| known_mistake | キーに挙げた失敗を作業指示・決定・報告として採用した。例を正しく引用した後でも、最終行動が失敗ならこちら。規則抜けは、完全な手順を返したのに必要操作を省いた場合も該当。 |
| other_failure | 判定可能な回答だが必要な行動を示さず、既知の失敗とも一致しない。例「よく調べます」で終わる、別の商品を選ぶ、対照の割り算を単に間違える。 |
| cannot_tell | 記録切れ、相反する最終指示でどちらを採ったか不明など、作業判断を観測できない。ツール呼出しが無いことだけではこの判定にしない。 |

種類別の2例ずつ（採点用発話・判定・根拠）は [採点練習12例](grading/examples.json)。対照で関係のない記憶により答えを変えたり作業を差し止めたりすれば known_mistake。無関係な事実に触れただけで結果を変えない場合、過剰適用には数えない。outside は同じ4値で記録するが主集計から外す。

**主集計**は各条件で44機会（対象36＋対照8）の pass / 44 と known_mistake / 44。cannot_tell、other_failure も分母に残し、4値の内訳を併記する。各機会で条件間の「失敗→合格」「合格→失敗」を突き合わせ、6種類別と対照だけの過剰適用率も出す。欠測を pass と数えない。主集計では対象外4件を除く。全48件の観測ログでは、未呼出試行も保持する。

**再指摘（BR-20）**は採点者の known_mistake と別の結果。所有者のルールが成立した後の同じ対象・同種の行動機会を一度ずつ数え、実際の訂正発話を受けた回数を別記する。この固定セットは各機会一回で、訂正を自動挿入しない。訂正を観測する追跡がなければ「再指摘未測定」、同種機会0も「未測定」。盲検採点の失敗率だけで長期の再発率を主張しない。
