# Split discrimination measurement

The numeric suffix determines the split. All 76 odd queries were development data. The even half was confirmed once per selected retrieval method after freezing the product at commit e8bb0833977bda8718cef94803dd8c4f1eb68494. The archive, scene data and expected answers were unchanged. The previous study had published first pages and token receipts. It did not retain score vectors. The original question was rerun on DEV to acquire them. TEST comparisons use the previous study's committed core and extended-timeout Jev observations.

Recompute the first-page comparison with `python3 verify/selection/report.py`. Replay the threshold screen with `python3 verify/selection/sweep.py`. Rebuild the temporary baseline instrument and rerun all DEV core variants with `python3 verify/selection/core_variants.py`. The four grid parameters are query coverage percent, fraction of the best score in percent, whether matching non-target/action scene terms add a second vote, and whether to filter nonmatching actions for a structured target. In the final structured judge filter an explicit target and action with no scene are required. No evaluation code or grading data is linked into the product.

The development objective was the most exact first pages with at most ten percentage points less required recall than the corresponding baseline. Existing acceptance cases were a separate gate. At a 19% floor English partial-overlap S1 regressed. At 12%, the 60% relative cut with trigger evidence passed the scene gate and beat the other feasible grid settings. Near misses are omitted. An empty accepted set reports none. The selection gate is independent of usage and leaves action-bound rules eligible.

The two proposed alternative questions are archived in questions.json. Each ran live on the same DEV archive at threshold 0.50 with a 10-second port and 9-second adapter limit. The saved score vectors support threshold and within-group probability-gap screens without further HTTP traffic. In the screening table, acceptance precedes page packing. The final chosen parameter was verified through the actual port and first page. Margin cuts of 0.10 and 0.20 against the strongest rule for the same structured target/action provided no advantage under the selection criterion. On two independent DEV draws, 0.65 crossed the recall-loss limit once. The original wording with threshold 0.60 satisfied the recall constraint in both draws. The Jev configuration example sets this explicitly; other judge commands keep their own calibration.

On the original DEV replay, shared-phrase losses clustered in four multi-rule queries (Q011, Q043, Q087, Q091). Eight required rule instances were absent. Sharing one phrase did not establish every required secondary procedure. More literal trigger wording reduced forbidden returns but lost required rules. On the separate live runs, scores varied between calls to the same model.

The loose prefilter required 9.5% query-term coverage for text queries and an action match for structured queries. It discarded 13 required instances among 68. With the instruction wording it reduced input tokens from 767,016 to 124,195. Five empty candidate lists incurred no provider request. Structured-only prefiltering preserved all 68 required instances, reduced candidate submissions from 5,032 to 4,920, and used 750,118 input tokens with that wording. The timing measures include a local capturing process. Most queries still send all 72 rules. The extra DEV run at the default port limit had 76 successful judge replies. The frozen TEST run used 10 seconds for comparability with the earlier complete probability run.

No requirement wording changed. Exact-set improvement on TEST accompanied lower required recall. For core, the held-out loss (8/76, 10.5 percentage points) exceeded the DEV loss allowance slightly. None-correct remained 0/16 for core on TEST.

## Independent confirmation of the two tiers

The preceding TEST comparison informed the request for a candidate tier. That even-numbered split was never rerun for the two-tier change. Commit d4ed3303e25b903efdce01b29800f7933f4e3fc1 froze the new product before the merge of the separate holdout data into this branch. The fresh 80 observations per method use the same frozen 72-rule archive, new recall processes and first pages. The earlier executable and adapter used the pre-PR-16 policy and threshold 0.50. The new executable used the frozen strict rule policy, or Jev at 0.60 with the lower bound of 0.30. Both judge conditions used the same 10-second port and 9-second adapter budgets.

The candidate tier restored the requested DEV union recall for both policies. On the independent holdout, Jev exposed 79/80 required instances across both tiers and returned 60/80 in the confirmed tier. Compared with the original Jev run, strict forbidden opportunities decreased to 8/80 from 15/80. Strict exact sets also decreased to 56/80 from 58/80. All 20 negative queries had no confirmed result, eight of them returned unconfirmed candidates. A caller that automatically consumes candidate headings would lose the distinction. No parameter was adjusted after this measurement. The candidate tier measures availability of a short reference; it does not establish that an agent followed the reference or made a better decision.

The complete four-way comparison, including time, byte counts, tokens and negatives, is in results/two-tiers.md. Recompute it with `python3 verify/selection/tier_report.py`. The earlier single-tier tables remain separately labelled in results/summary.md.
